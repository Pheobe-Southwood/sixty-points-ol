# 机器重演：结算那一刻把整副牌重发给三个机器人

**这是对 ADR-0015 的补充，不是修订**：那条定的是「机器人坐在座位上怎么打」，
这条定的是「一副**已经打完**的牌，能不能重打一遍给人看」。

动机是战报的读法。战报现在能把真实那副讲清楚（定约、算式、结论、级别），但它回答不了
复盘时最自然的那一问 ——「这三张底牌埋得对不对 / 这个定约撑不撑得住」。真实那副只有一次选择，
而三个机器人在同一副牌上的选择是**确定性**的，可以拿出来当对照。

- **起点是整副重演（含叫牌）**：从发牌后的原始三家手牌开始，叫牌、埋底、出牌全部由策略重走一遍。
  于是**定约与庄家都可能与真实那副不同**（机器人自己叫自己的），展开体头行写的因此是**重演的**定约。
  若只从真实定约接着打，重演就只是「这条路线打得对不对」，而复盘想问的是「这副牌本来该怎么叫」。
- **全 pass 如实显示**（约 5%）：重演自己也可能三家 pass，那就是一副会被作废重发的牌。
  确定性策略下不许靠「再摇一次」凑一个定约出来 —— 那会让同一条记录每次打开都不一样，也就没资格当对照。
- **在结算那一刻同步算完**：`applyTableAction` 收到 `dealScored` 时，`state.deal` 里还留着这副的
  全部隐藏信息（三家手牌、`originalKitty`、`trickHistory`），**此刻不落库就永远算不了** ——
  下一次 `deal` 会把它们冲掉。存档是一次性的只读记录，之后不再重算。两处易错的重建：
  - **庄家的原始 17 张**要**去掉拿上来的 3 张、加回埋下的 3 张**才能还原（拿上来的底牌在埋底后
    已并进手牌，埋下的那 3 张则已出局），即「**打出的 17 = 原始 17 ∪ 拿上来的底牌 − 埋下的底牌**」。
    写错的话重建出的牌会重复、缺张 —— 牌数守卫（每座 17 张 + 底 3 张，且互不重复）会当场报错。
  - **前置级别**取 `levelChanges.from`（结算前的值），不是 `state.levels`（结算后的值）——
    级别决定主牌大小，用错等于让重演打在一个不存在的将牌环境里。
  - 失败只记一条日志（`机器重演失败（第 N 副）`），**不阻塞结算**：重演是锦上添花，结算才是主线。
    代价是那一副在界面上落到「没有记录」那句文案里。
- **只走一个新的 REST 读端**（`GET /api/tables/[code]/replays`）：**不进 SSE / `StreamPayload`**
  （重演是按需查看的静态数据，塞进每一帧只是白涨负载，MCP 的 wire 也就一行都不用动），
  **不新增 MCP 工具**（工具面是「参与对局」的能力，不是回放存档）。任何身份都能看 ——
  结算后牌面本就全公开。
- **入口只有两处**：战报**逐副卡**卡尾与**结算弹窗**（排在升级表之后）。升级表**没有**入口 ——
  它说的是真实进度，重演是每副的对照。展开体复用结算那三件套
  （`contractText` / `ScoreEquation` / `VerdictBadge`），所以弹窗、战报、重演三处读法一致，
  没有第二份算式实现。数据通道由页面持有（一次拉全表 + 按副号取），组件不发请求；
  老副没有记录时如实说一句，不玩「按钮消失」——那看起来像功能坏了。
- **命名**：叫**机器重演**，不叫「模拟」—— 它没有蒙特卡洛、没有搜索，就是同一副牌用同一个
  确定性策略重打一遍（`_Avoid_` 已记进 CONTEXT.md）。

**边界（最该记住的一条）**：重演的手牌是从 `trickHistory` 还原的，**数组序不等于发牌序**；
而策略里有几处 tie-break 是按下标做的（埋底的 `a.i - b.i`、垫牌用的稳定 `sort`）。
于是重演是「这副牌**当集合** × 确定性策略」的唯一结果，**不必也不可能**逐字复刻当初那桌自己
打出的那一份 —— 当初那桌的手牌序从来没有被保存过。`packages/bot/test/sim.test.ts` 钉的
强形式（逐字相同）只在「那三个座位**也是机器人**」时成立，那是同一份输入的一个合法特例；
另外两条是确定性（同输入同输出）与摘要自洽（`庄分 + 闲分 = 100 − 底分`）。

被否的替代：**前端现算**（要把整副隐藏牌发给浏览器，等于把「结算前看不见」那堵墙拆掉）；
**塞进 SSE 每帧**（白涨负载，且 SSE 负载形状一动就得连 MCP wire 一起动）；
**加一个 MCP 工具**（回放存档不是对局能力，会污染工具面的语义）；
**全 pass 就重发到有定约为止**（破坏确定性，同一条记录会随打开次数变）；
**结算之后再懒算**（那副的手牌已被下一次 `deal` 冲掉，只剩摘要 —— 而重演要的正是完整牌）。

后果：`packages/engine` 加一个 `dealWith(hands, originalKitty, dealerSeat, dealNo)`
（`newDeal` 改为委托它，引擎仍是纯函数）；`packages/bot` 加 `sim.ts`（`simulateDeal`，
**仍只吃个人视图**，纯度测试的白名单同步加它）；数据库多一张 `replays` 表
（`(table_id, deal_no)` 主键、`ON CONFLICT DO NOTHING`，开新对局时清空）；
服务端在结算事务里多跑一次确定性策略 —— 代价就是「把这副牌按策略走完」，没有搜索也没有模拟，
本轮没有单独计时（冒烟整轮的墙钟时间是观察口），仍是单实例进程内的事，与 ADR-0001 的前提一致。
守卫：`apps/web/test/table-chrome.test.ts` 的 `replayEntryCheck`（两个入口 + 那三件套 +
通道归页面，含五条反证）、`apps/web/test/bot-guard.test.ts`（读端只读、浏览器形状零策略依赖）、
`apps/web/scripts/smoke.ts`（存档逐副对得上、无凭据 401）。结算弹窗与战报**都按需渲染**
（`summaryOpen` 初值 false；战报只在 `active === 'report'` 时进 DOM），`ui-check` 够不到这个功能，
所以判据落在源码层与那几条端到端脚本上。
