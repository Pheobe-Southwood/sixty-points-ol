# MCP 工具负载投影：一副牌的投喂量砍到五分之一

ADR-0010 把「一个身份能看到什么、能做什么」包成了 MCP 工具面，但没算过**这副面要说多少话**。
真接上宿主跑了才知道：一轮牌打完，模型读进去的是百万字符量级。这一条记录怎么把它砍下来，
以及砍到哪一步为止 —— 以及为什么不继续砍。

## 决策

1. **出参默认走紧凑投影**（`packages/mcp/src/project.ts`）：牌面写成短码（`"S14"` = ♠A、
   `"j0"` = 小王）、删掉重复字段、跨副历史压成计分行。`verbose: true` 仍可拿回引擎类型逐字的那一份。
2. **动作自带等待**（`wait`，默认 true）：动作成功后阻塞到下一次轮到你，返回那一刻的局面 ——
   每个回合因此只有**一次**工具调用，也只会被投喂**一份**局面。
3. **合法性由状态直接给**（`turn.legalBids` / `turn.legalPlay`），不再让模型逐张试探；
   `check_play` 改成一次验多组候选，留作兜底。

## 实测（座位 0 打完一副，RNG 固定）

| 指标 | 改前 | 改后 |
| --- | --- | --- |
| 一副牌的实收负载 | 116,278 字符 | **35,636** |
| 模型累计读入（每个请求都重发整段会话） | 1,845,222 | **401,156** |
| 每副的 MCP 调用数 | 38 | **21** |
| 结算那一刻的单份局面 | 6,232 | **约 2,760** |
| 工具面 schema（每个请求都重发） | 5,451 | **4,656** |

一整局（7 副，打到结束）：153 次调用 · 实收 396,503 字符 · 累计读入 26,710,960 · 最大单份 4,402。

## 为什么是这几刀

**累计读入是二次的。** 宿主每个请求都会重发整段会话与工具面 schema，第 i 份结果会在之后的
每个请求里再出现一次，所以整局的账 ≈ 回合数² × 每份大小的一半。这一条决定了优先级：

- **回合数比每份大小更要紧**：动作自带等待把每副的往返从 38 降到 21（≈ 1.8 倍），
  而它对累计读入的效果接近平方 —— 单看整局，这一刀就值好几倍。
- **逐张试探是最贵的用法**：每回合多探 3 次 `check_play` → 累计读入变 **2.85 倍**，
  多探 17 次 → **16.2 倍**（本仓库的 `mcp-check` 自己当初就是这么探的）。
  所以现在把「该跟哪一门、要不要垫牌」做成 `turn.legalPlay` 里的两三个字段直接给出来 ——
  几行字换掉整个回合。
- **重复字段是纯浪费**：结算时 `deal` 里 `captured[].cards` 与 `trickHistory` 是**逐张重复**的
  同一批牌（51 张 = 51 张，有测试证明），`trickHistory` 本身又占了负载一半以上。

## 与 ADR-0010 的关系

0010 写的是「工具返回的是引擎的 `PersonalView` **原样**……卡牌对象保持引擎形状」。
这一条把它**收窄**为：默认给紧凑投影，`verbose: true` 时仍是原样。

**浏览器那份负载一字未动**：`/view`、SSE 与 `wire.ts` 里声明的 `PublicView` 照旧逐字，
`mcp-check` 的形状守卫仍逐字段核对真实响应 —— 变的只有 MCP 这一侧怎么把同一份负载说给模型听。

这不是 0010 当初担心的「第二套视图类型」，因为它没有变成第二个来源：

- 投影是**单向派生**的。`project.ts` 只 import 引擎的**类型**与本包的编解码，静态守卫
  （`test/project.test.ts`）钉住这一点 —— 它读不到牌局状态，也就没有能力编造事实；
- 字段**只减不增**，每个字段都追得到服务器负载里的一个字段，字段清单还有逐字守卫；
- `Card` / `BidCall` 仍是唯一契约：编解码是双向的，**出参与入参同形**
  （`you.hand` 的元素可以原样喂回 `play`/`bury`），所以没有「重新编码花色字形」那一类错。

## 明确的取舍

- **`captured[].cards` 不再给**（只留 `capturedPoints`）：要牌就翻 `trickHistory`。
- **已完成的墩不再给 `leaderSeat`**：可推 —— 第一墩由庄家领出，之后每墩由上墩赢家领出；
  当前这一墩仍给（它是出牌的直接约束来源）。
- **一副牌写成 `"0:C5 H3"`**（座位 + 牌码，一手内空格分隔）：出参用这个写法，入参仍是
  `cards: ["C5"]` 数组。座位与「哪几张是一手出的」都没丢。
- **`history` 每条只留计分行，最多 10 副**。实测本仓库的驱动打完整局通常只要 7 副
  （闲家涨级很快），所以常见情况下这个上限**等于没裁**；它的作用是给长局一个上界。
  真裁掉时用 `historyOmitted` 如实报数 —— 不许让调用方以为历史是全的。

## 后果与遗留

- **跨副的账仍然是二次的**。整局 26.7M 字符里约九成是「回合数 × 已经投喂过的前缀」，
  再往下只有一条路：**增量响应**（客户端带游标、服务端只回变化）。那要服务端记住
  「这个客户端看到哪了」，与 0010 的「无状态 + 每条负载自包含」直接冲突，所以**没有做**，
  留在这里当作已知的下一步。
- **工具面 schema 只降到 4,656**：13 个工具每个都有约 85 字符的 JSON Schema 底板
  （`$schema` + 包装），这是 SDK 的生成方式决定的；再降只能减工具、或删掉字段描述
  （那会伤害自描述性，有客户端不注入 `instructions` 时工具就说不清了）。没有做。
- **共用的句子只说一遍**：`initialize` 的 `instructions` 里讲清一副牌的节奏、牌码格式与
  「座位由服务端定」；每个工具的描述仍自给自足，但不再各自重复一遍。
- 顺手修掉一个说谎：`legal_bids` 原先只看 `deal.highestBid`，叫牌结束后（埋底/出牌/结算）
  仍然返回一整套「合法叫品」。现在按阶段门返回空表。
- **预算进了测试**：`packages/mcp/test/payload-budget.test.ts` 用内存版服务器走完整副与整局，
  卡住调用数、实收、单份与整局累计；「非空转」由「同一条路上 `verbose` 必须超预算」证明。
  `scripts/mcp-check.ts` 另对**真服务器**卡一次调用数与字节数。
