# 弱一致信息要推、非幂等写不重试

ADR-0010 让 MCP 工具面上了桌，两处收尾没做完，都是「值对了但没送到」的同一类问题的两个面：

- **在线与入座没人推**：`touch()` 只改了 `lastSeen` 这张表，`enterTable` 干脆没有广播。
  浏览器玩家入座后**必然**连上 SSE（`stream` 在连接时会广播一次），于是「入座总能把别人的屏幕刷新」
  这个隐含前提一直成立 —— 直到 MCP 座位出现：它是第一个**没有 SSE 连接**的客户端。
  人类屏幕上会一直显示「还差 1 人」「开始第一副」是灰的、那颗点也是灰的，直到某个人先出一次牌。
  守卫也漏了：当时的在线断言是**直接读 `/view` 的服务端值**，所以它绿着，屏幕照样是旧的。
- **非幂等写被自动重发**：`http-api` 的 `request()` 只要「没读到响应」就重发一次，而它服务的
  写路径（`POST /action`、`POST /api/tables`、`POST /join`）在服务端**没有幂等键**。
  于是响应在服务端提交之后断开时：一次已经生效的动作被报成失败，或者一次 `create_table`
  在服务端留下两张桌（第一张是永远不会被用到的孤儿桌）。

## 决策

1. **状态变化在 `tables.ts` 里广播，路由不再负责推送。** `enterTable` 的两条变更分支、
   `takeSeat`、`leaveSeat` 各自在变更后 `broadcast(table.id)`；`seat` 路由原来那两处广播收进 lib。
   规则收敛成一句话，下一个人加一条变化路径时不会只改一半。
2. **「离线→在线」翻转时广播，按身份通知他出现的所有桌。** `hub.touch(userId)` 返回
   `boolean`（这次请求是不是一次翻转），`tables.ts` 据此 `announce(userId)`。
   - 为什么不是「每次请求都推」：`wait_for_turn` 每 1.5 秒读一次局面，那是刷屏。
   - 为什么是**所有桌**而不是当前这张：在线的判定（`isRecentlyActive`）本来就是**身份级**的
     （按 `userId` 存），一个在 A 桌坐着、拿 B 桌的码轮询的 agent 不该在 A 桌一直显示离线。
     `tableIdsOf(userId)` 就是「他出现在哪些桌」（`seats ∪ spectators`），一年也跑不了几次 ——
     一个窗口内每个身份至多翻转一次。
   - **不改 `myTables` 的返回形状**来做这件事：那份形状有浏览器消费者，等于 wire 形状。
3. **`broadcast` 用工作列表，不用递归。** 推送会让每条连接重新取一遍负载，而取负载本身可能
   又触发一次翻转广播。直接递归是「推送里再推送」，深度随连接数走；而「推送中直接丢弃」会**丢帧**
   （同一轮里后触发的那个人，在先算出的帧里仍然是灰的，且不会有第二轮）。所以排进队列、本轮结束
   后继续排空，`flushing` 在 `finally` 复位。不会自激：触发只有一个来源 —— 某人自己的请求。
4. **写路径一次都不重发。** `http-api` 的重试只对幂等读（`GET /view`、`GET /api/tables`）开放，
   由调用方显式给 `retries: 1`，默认 0。写路径失败时如实说：
   `无法确认这次请求是否已经生效（…）：先用 get_state / list_my_tables 核对现状，再决定是否重发`。
5. **`status === 0` 不算「服务器拒绝」。** 没拿到响应不是服务端的判定，套上那个前缀会把人引向
   错误的下一步（「服务器拒绝」暗示没生效，而它恰恰可能是生效了才丢的响应）。

## 后果

- 入座帧与「刚上线」帧会出现在别人的屏幕上，`ready`/按钮/座位点不再滞后。
  这不影响正在选牌的人：客户端只对「让选择失去意义的帧」清空选择，名单与在线点的变化不在其列
  （`selection.test.ts` 已有的断言，本次不动客户端）。
- 多推的帧是**有界**的：入座/离座各一次；在线翻转每个身份每个窗口至多一次（每张他出现的桌一帧）。
- **已知保留：绿点不会自动转灰。** 60 秒窗口到期时没有任何触发者（MCP 客户端已经停手），
  要让它在没事件时自己变灰，得在服务端挂定时器 —— 模块级 `setInterval` 在 dev 热重载下会叠加，
  还给单实例进程加一条生命周期。代价与收益不成比例，所以**知情不修**：这颗点在停手后可能多绿一会儿，
  而它本来也不参与任何规则判定（见 `CONTEXT.md` 的 **在线**）。
  （**断线**那一半后来由 ADR-0013 补上：连接真的断了就立刻作废窗口。这里留下的只是
  「连着但没人动」的那种绿。）
- 重试策略的代价：真遇到瞬时网络抖动时，写路径会把失败**如实报上去**，由调用方核对后重试，
  而不是工具面替它猜。换来的是不会重复执行 —— 对一个「动作要么生效要么不生效」的游戏来说，
  这个交换是值的。

## 守卫

- `apps/web/test/presence.test.ts`：`touch` 只在翻转那一次返回 `true`；`broadcast` 可重入
  （推送里再触发会排到本轮之后、不爆栈、不丢帧）、会摘掉抛异常的连接、没有连接时是空操作。
- `packages/mcp/scripts/mcp-check.ts` 的**推送守卫**（对真服务器、真 SSE 流、真工具调用，
  两条传输各一次）：新建一张桌 → 人类连上 SSE → 另一条凭据**经该传输**调 `join_table` →
  断言收到「第三个座位已被占」的帧，再断言收到「他在线」的那一帧。
  这正是把审查用的 `probes/presence-push.probe.mjs` 变成永久断言 —— 只读 `/view` 的守卫
  看不见这个缺陷，所以守卫本身必须走推送这条路。
- `packages/mcp/test/http-api.test.ts`（注入 `fetchImpl`，全确定性）：GET 失败重发一次；
  POST 失败**只发一次**；「服务端已提交、响应体读失败」时消息含「无法确认」且含指路；
  `create_table` 在该场景下只有一次 POST（孤儿桌无法再复现）；4xx 不重发且原话保留。
- `apps/web/test/docs-paths.test.ts`：README 里提到的 `apps/…`、`packages/…` 路径必须真实存在
  （同一 PR 里 `help.ts` 搬进引擎包，代码引用都改了、README 那一行漏了）。存在性按**文件或目录**算，
  并排除构建产物（`apps/web/build`、`.svelte-kit`）—— 第一版没排除，于是在「刚好构建过」的本机绿、
  在干净检出的 CI 红：**守卫自己被 CI 抓了一次**，这正是它该干的事。
- 三处新断言都按 AGENTS 规则 9 做过「注入违规 → 变红 → 逐字节还原（sha256 比对）」。
